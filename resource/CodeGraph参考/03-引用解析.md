# CodeGraph 实现参考（03 · 引用解析）

> 把 `unresolved_refs` 跨文件绑定成真边的阶段。主类 `ReferenceResolver`（`src/resolution/index.ts:203`），子模块 `import-resolver.ts` / `name-matcher.ts` / `callback-synthesizer.ts` / `frameworks/*`。

## 1. resolveAll 主流程（`index.ts:608`）

```
resolveAll(refs):
  warmCaches()                         // 预载所有节点到内存，加速查找
  for ref in refs:
    result = resolveOne(ref)          // 单条解析
    result ? resolved.push : unresolved.push
  return { resolved, unresolved, stats:{total,resolved,unresolved,byMethod} }
```

- `byMethod` 统计每条引用由哪种策略解析（`import` / `name` / `framework:xxx` / `function-ref` 等）。
- 进度每 1% 回报一次（:644-651）。

## 2. resolveOne 解析策略链（`index.ts:765`）

顺序（每条都有 `gateLanguage` 做语言族守门，避免跨语言误连）：

1. **跳过内建/外部引用** `isBuiltInOrExternal`（:767）。
2. **CFML 组件路径**（继承 `extends/implements`）：点号/路径形式直接走专用 path matcher（#1152）（:780-786）。
3. **快速预筛** `hasAnyPossibleMatch`（:788-810）：若全代码库都不存在该名字、且不匹配本地 import、且未被任何 framework claims，直接 return null。预筛里 `existenceName` 处理 ArkTS 前导点（`.titleStyle`→`titleStyle`）、Nix 路径 import 绕过（:799-810）。
4. **函数即值引用** `function_ref`（#756）（:817-831）：`this.x` 只解析到本类成员；否则先 import 解析（最精确跨文件信号），再 `matchFunctionRef`（同文件优先、跨文件唯一、仅 function/method 目标）。不走下面框架/模糊策略。
5. **JVM FQN import**（:836-837）：`import com.example.Bar` 直接走 `qualified_name` 索引，无歧义（多个 `Bar` 也能区分）。
6. **候选策略**（:849-913）：
   - **策略1 框架解析** `framework.resolve`（:856-862）：跨语言桥（如 Drupal `routing.yml`→PHP controller、RN JS→native `calls`）保留；`confidence>=0.9` 立即返回，否则入候选。
   - **策略2 import 解析** `resolveViaImport`（:865-869）：conf>=0.9 立即返回，否则入候选。
   - **策略3 名字匹配** `matchReference`（:890）：有语言门（Nix 仅同文件，见下）；入候选。
   - PHP include / Cobol copybook / Nix path import / Terraform 只走 import 解析，不回退名字匹配（错误边比无边长，#660）（:881-887）。
7. **链式调用延迟** `deferredChainRefs`（:915-935）：`calls` + 链式语言（`a.b.c()`）/ PHP `$this->prop->method()` 首轮解不出时延迟，待 `implements/extends` 边存在后的 conformance pass 再解。
8. 返回候选中**最高 confidence** 者（:938-941）。

### hasAnyPossibleMatch（:676-741）
用预建 `knownNames` 集合做存在性预筛，巧处理分隔符：
- 点号 `a.b`：`receiver`/`member` 任一存在即可；JVM FQN `com.example.foo.Bar` 取最后段 `Bar`；
- `::`（Rust/C++ `a::b::c`）：取最后段 `c`；
- 单 `:`（Lua `lg:log`）/ `$`（R `lg$log`）：取 member/receiver；
- 路径型（`snippets/drawer.liquid`）：取文件名。

## 3. createEdges：边类型提升与溯源标记（:947-1009）

把 `ResolvedRef` 转成真边时做语义提升：

- `function_ref` → `references`（内部注册站依赖回调，标记 `metadata.resolvedBy='function-ref'`）（:949-955）。
- `extends` → `implements`：当目标是 interface/protocol 且源不是 interface/protocol（:958-966）。
- `calls` → `instantiates`：当目标是 class/struct（无 `new` 关键字的语言 `Foo()` 也能识别为实例化）（:973-978）。

**溯源元数据**（复活跨文件边的关键，#1240）：
- `refName` = 原始引用文本（:999）；
- 边类型被提升时额外记 `refKind` = 原始 kind（:1000）；
- `function_ref` 额外记 `fnRef:true`（:1005）。

这样当目标节点因 re-index 被删时，边能**忠实复活**为原始 ref 重解析；而从目标节点名重建 ref 会丢失 receiver/qualifier 上下文导致误绑，故无 refName 的合成边**不**复活（:989-1005）。

## 4. import-resolver.ts（import / 路径解析，`src/resolution/import-resolver.ts`）

- `resolveViaImport`（被 resolveOne 策略2 调用）：按本文件 import 映射解析符号。
- `resolveImportPath`（:58）：解析模块路径（含相对路径、扩展名推断）。
- `extractImportMappings`（:660）：提取文件内 import 映射（localName→specifier），供「重导出链」与预筛 `matchesAnyImport` 使用。
- **barrel 重导出链**：`import { login } from './barrel'` 而 barrel 有 `export { signIn as login }`——名字无声明，靠 import escape 让重导出链解析（:748-760, :791-793）。
- `applyAliases`（`path-aliases.ts`）：tsconfig/webpack 等 path alias 解析。
- `resolveWorkspaceImport`（`workspace-packages.ts`）：monorepo workspace 包解析。
- `isNixPathImportRef` / `isPhpIncludePathRef` / `isCobolCopybookRef`（:46/:616/:629）：语言特定路径引用判定（只走 import 解析，不回退名字匹配）。
- `loadCppIncludeDirs` / `clearCppIncludeDirCache`（:408/:425）：C/C++ include 目录缓存。

## 5. name-matcher.ts（名字匹配，`src/resolution/name-matcher.ts`）

- `matchReference`（:1899）：对给定 ref 在节点名上做匹配并返回 `ResolvedRef`（带 confidence）。
- 语言门控：Nix 无跨文件命名空间，跨文件名字匹配按构造是错的（每个模块 inherit 同样的 nixpkgs helper），故 Nix **仅同文件匹配**（:891-910）。

## 6. callback-synthesizer.ts（回调/动态派发合成边，`src/resolution/callback-synthesizer.ts`）

- 为 grep 跟不到的动态关系合成边：回调注册、事件监听、`fnRef` 函数即值等。
- 产出边标 `provenance='callback'` 或 `heuristic'`，与静态 AST 边区分（供遍历/`buildFlowFromNamedSymbols` 识别动态边界）。
- 这是「确定结构 + 推断关系解耦」原则的体现：动态派发补在合成层。

## 7. frameworks/*（每框架解析器，`src/resolution/frameworks/`）

- 每框架一个文件：`express.ts` / `react.ts` / `nestjs.ts` / `vue.ts` / `laravel.ts` / `java.ts` / `go.ts` / `rust.ts` / `python.ts` / `swift.ts` / `react-native.ts` / `csharp.ts` / `terraform.ts` / `astro.ts` / `svelte.ts` / `play.ts` / `fabric.ts` / `drupal.ts` / `expo-modules.ts` / `cargo-workspace.ts` / `cics.ts` / `goframe.ts` / `ruby.ts` / `swift-objc.ts` / `mixed-ios` 桥等。
- 每个框架解析器实现 `resolve(ref, context)` 与可选 `claimsReference(name)`：
  - `resolve`：把框架特定引用（如 Express `app.get('/x', handler)` 的 handler、React 组件 props、NestJS 路由 controller、Vue SFC）绑定成边或合成节点。
  - `claimsReference`：让框架「认领」某名字，跳过通用预筛（:807）。
- 框架边标 `provenance='framework:<name>'`，可在展示时说明来源。
- 还有 `c-fnptr-synthesizer.ts`（C 函数指针）、`go-module.ts`/`goframe-synthesizer.ts`（Go module）、`swift-objc-bridge.ts`（Swift/ObjC 互桥）。

## 8. 解析阶段与建库阶段的衔接

- 建库（extraction）只产出 `unresolved_refs`（status=pending）+ 文件内 `references` 边。
- 解析（`resolveAll` → `createEdges`）把 pending 解析：成功删行、建真边；失败留 `failed` + `name_tail`（见 01 §4）。
- 同步（`sync`）后重跑解析：先解析新 pending，再重试 `failed`（按 `name_tail` 匹配新符号）（#1240）。
- 全部走 `resolveAndPersistListYielding`（:1070）/ `resolveAndPersist`（:1014）批量落库，带 cooperative yield 防止长阻塞。
