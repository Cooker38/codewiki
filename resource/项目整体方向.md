## 项目知识库系统
## 一、产品定位与目标
### 1.1 定位
一个基于代码结构自动生成项目文档的知识库系统，通过 Agent 为开发人员提供精准、可溯源的代码知识问答。

### 1.2 解决的核心问题
+ 新人上手靠口头传授，缺乏结构化指引
+ 代码变更后文档滞后，维护成本高
+ 传统 RAG 方案成本高、精度低（依赖向量检索，容易产生幻觉）
+ AI 编程助手缺乏项目上下文，无法精确回答代码细节

### 1.3 设计目标
| 目标 | 说明 |
| --- | --- |
| 自动生成 | 代码合并后自动更新 6 类核心文档，无需人工干预 |
| 精准溯源 | 每个文档段落均可追溯到源代码文件+行号 |
| 低成本 | 放弃向量检索，采用“Wiki 主答 + 图谱补深”的确定性检索链路 |
| 即查即用 | 提供 MCP Server / Agent Skill 接口，供 AI 助手调用 |


## 二、核心设计思路
### 2.1 总体逻辑
+ **代码解析层**：Tree-sitter 提取符号、调用关系、导入关系，存入 SQLite
+ **文档生成层**：Agent 将结构化代码事实翻译为 6 类 Markdown 文档，文档中嵌入代码锚点（`<!-- code_ref: file_path::symbol_name -->`）
+ **查询路由层（Wiki 优先 / 图谱兜底）**：
    1. **Agent 自动发现 Wiki**：进项目时自动读 AGENTS.md（生态标准行为），按指路找到 `wiki/quickstart.md` → 通过内链导航按需读取各 Wiki 页面。Wiki 是可见目录下的普通 Markdown 文件，Agent 直接读，不走 MCP
    2. **不足则查图谱**：Agent 判断 Wiki 笼统/缺失时，从文档锚点提取符号，调图谱 MCP 工具（`codewiki_callers` / `callees` / `impact` / `node` / `search` / `explore`）获取聚合代码事实——传递性调用链、影响半径等 grep 算不出的信息只在图谱里

### 2.2 核心原则
1. **文档与代码同源**：文档全量由 Agent 生成，代码变更即文档变更
2. **锚点即索引**：通过文档内嵌的代码锚点实现文档↔图谱的双向跳转
3. **确定性优先**：不依赖向量相似度，走“关键词定位 → 读原文”的确定路径
4. **增量更新**：每次代码变更只重写受影响的文档片段，不全量重建


## 三、文档体系（全自动生成）
共 6 类文档，全部由 Agent 自动生成，存放于 `wiki/` 目录（可见、gitignore、不提交）。`wiki/quickstart.md` 作为入口索引页，包含项目概述 + 各文档链接列表（对标 openwiki 的 quickstart.md 设计，AGENTS.md → quickstart.md → 内链导航）：

| 文档类型 | 路径 | 内容说明 |
| --- | --- | --- |
| 项目概述 + 快速开始 | `README.md` | 项目简介、技术栈、本地运行步骤 |
| 系统架构 | `architecture/` | 整体架构图（C4）、模块边界、核心设计决策（ADR） |
| 数据库表文档 | `database/` | ER 图、表结构、索引策略、迁移说明 |
| API 接口文档 | `api/` | OpenAPI 规范、接口说明、请求/响应示例 |
| 模块/核心功能 | `modules/` | 各模块职责、核心类/函数说明、调用关系、典型用法示例 |
| 运维调试 | `runbooks/` | 部署指南、配置项说明、常见故障排查 SOP |


**关键约束**：每个文档段落必须嵌入代码锚点，格式为 HTML 注释：

```markdown
## DiscountCalculator 模块
<!-- code_ref: src/pricing/calculator.py::DiscountCalculator -->
提供折扣计算能力，支持会员等级和优惠券叠加...
<!-- code_ref: src/pricing/calculator.py::calculate_discount -->
```

Agent 回答用户问题时，若判断 Wiki 不够详细，则从该注释中提取符号名，去 SQLite 查源码或调用链。


## 四、知识图谱（CodeGraph 实现）
基于 SQLite + Tree-sitter 实现轻量级代码图存储。放弃 Neo4j。注：图遍历在 CodeGraph 中是应用层 BFS/DFS + 预编译查询（非递归 CTE），详见 `resource/CodeGraph参考/04-图查询与遍历.md`。

### 4.1 节点类型（22 种，定义在 `src/types.ts:18` 的 `NODE_KINDS`）

| 类别 | 具体 kind |
| --- | --- |
| 文件/模块 | `file`, `module`, `namespace` |
| 类型声明 | `class`, `struct`, `interface`, `trait`, `protocol`, `enum`, `type_alias` |
| 成员 | `method`, `property`, `field`, `enum_member`, `parameter` |
| 值/函数 | `function`, `variable`, `constant` |
| 导入/路由 | `import`, `export`, `route`, `component` |

**节点 ID 为内容寻址**（`src/extraction/tree-sitter-helpers.ts:18-30`）：

```ts
id = `${kind}:` + sha256(`${filePath}:${kind}:${name}:${line}`).slice(0, 32)
```

含义：行号一变 → ID 变。因此增量重索引后旧边引用的旧 ID 全部失效，必须用 `(filePath, kind, name)` 重新匹配目标（详见 4.3 跨文件边复活）。

### 4.2 关系类型（12 种 `EdgeKind`，`src/types.ts:48`）

关键在「两阶段落库」：**AST 阶段并不会把 12 种边全部直接写库**，而是分三层：

**① AST 阶段直接落库的边（2 种）**
+ `contains`：层级包含，`file→class→method→parameter`，遍历语法树时同步 push。
+ `references`：文件内的值读取（`tree-sitter.ts` 的 valueRef，`:885` 带 `metadata.valueRef`——同文件内对常量/变量的直接引用）。

**② 先记为「未解析引用」→ 再变真边（主体）**
`calls` / `imports` / `exports` / `extends` / `implements` / `instantiates` / `decorates` / `references`（跨文件）：AST 阶段**不生成边**，而是 push 一条带 `referenceKind` 的 `UnresolvedReference`（`tree-sitter.ts` 多处如 `:684`、`:3124` 的 `this.unresolvedReferences.push(...)`）。随后 **ReferenceResolver** 把引用按名字/限定符跨文件绑定到目标节点，才落成真正的边。例如 `extends` 是从各语言的 `extends_clause` / `base_clause` / `superclass` 等 AST 节点提取成引用，再绑定父类节点。

**③ 解析/合成层推得（非原始 AST 输出）**
+ `type_of`：变量/参数的类型标注
+ `returns`：函数的返回类型
+ `overrides`：子类方法与父类同名方法的重写

这三者不在 extractor 的 `referenceKind` 枚举里（全仓库无 `kind: 'type_of'/'returns'/'overrides'/'exports'` 的直接边 push），是 ReferenceResolver / 各 synthesizer（如 `callback-synthesizer`）在绑定阶段、比对类型注解与层级关系后推断出来的。

**一句话总结**：AST 只负责「建节点 + 连好层级 contains + 标出文件内引用」，对外关系（`calls`/`imports`/`extends`/`implements`…）全部降级为待解析引用，交给下游 ReferenceResolver 跨文件绑定——这也是它能把 grep 跟不到的动态派发（`calls` 合成边）也补进图谱的原因。

### 4.3 已确认的存储与增量机制（来自 `D:\codegraph` 源码查证）

> 详细证据见 `resource/CodeGraph参考/` 系列（01 存储层、02 建库、03 引用解析、06 增量同步）。

- **三表分离**：`nodes` / `edges` / `unresolved_refs`（外加 `files` / `name_segment_vocab` / FTS5 虚表 `nodes_fts`）。不要把对外关系一步到位只建 `edges`。
- **边唯一性索引**（`src/db/schema.sql:173`）：`(source, target, kind, IFNULL(line,-1), IFNULL(col,-1))`，`INSERT OR IGNORE` 去重，避免重复边灌入 callers/impact（#1034）。
- **`edges.provenance` 列**：合成边（框架/回调/启发式）标 `framework:xxx` / `callback` / `heuristic`，与静态 AST 边区分。
- **`unresolved_refs` 生命周期**：`pending` → 解析成功则删行 / 失败则标记 `failed` 并保留（`name_tail` = 引用名最后一段，供后续 `sync` 重试匹配新符号，#1240）。行跟随其 `from_node_id` 走 `ON DELETE CASCADE`。
- **`name_segment_vocab`**：标识符分词表（`WITHOUT ROWID`），随 `insertNode` 同事务物化（`src/db/queries.ts:342`），`splitIdentifierSegments` 把 `OrderStateMachine` 拆成 order/state/machine，供跨语言自然语言检索兜底；`file`/`import` 节点不写（免污染稀有度统计）。
- **跨文件边复活（#899 / #1240）**：re-index 删除文件会 `ON DELETE CASCADE` 级联删边。`storeExtractionResult` 先快照「源在别的未变文件、目标在当前重索引文件」的跨文件入边（带目标 kind/name），删除+重插当前文件节点后，按 `(filePath, kind, name)` 重解析目标新 id 重插；若重命名/删除导致找不到目标，则**复活为原始 `UnresolvedReference`**（边元数据 stamped `refName`/`refKind`），由同一次 sync 的解析阶段重绑或标记 `failed`。
- **codegraph 自身增量基于文件系统，不依赖 git**（参考事实，保留）：`src/extraction/index.ts:2305` `sync` 枚举当前源码文件，与 DB 逐文件 reconcile——先 `(size, mtime)` 预筛跳过未变文件，仅对疑似变更文件读 + `content_hash` 确认真变化；兼容非 git 项目，也能捕获 `git pull`/`checkout`/`merge`/`rebase` 后的工作区改动。
- **CodeWiki 增量方案（2026-07-12 已对齐，与 codegraph 故意偏离）**：**只响应本地 git 提交，不监听工作区文件变更（不用 fs.watch）**。要点：① 数据源 = 本地 git（不碰 GitHub 远端）；② init 时锁定当前 checkout 的分支名；③ MCP Server 进程存活期间自动轮询该分支引用（`auto_sync` 默认开启，可在 `.codewiki/config.json` 关闭）；④ 变更集 = `git diff --name-status C_old C_new`（A/M/D/R）；⑤ 只索引已提交代码，未提交改动不纳入；⑥ 非祖先提交（强推/reset/rebase 导致 HEAD 跳变）触发**全量重建**。详细流程见 5.1 / 5.3 / 5.5。


## 五、系统架构与数据流
### 5.1 模块分层
| 层级 | 模块 | 职责 |
| --- | --- | --- |
| 触发层 | MCP Server 进程内置 | init 时锁定当前 checkout 分支；MCP 进程存活期间自动轮询该分支引用（`git rev-parse <branch>`），检测到新提交即触发 `sync`。可通过 `.codewiki/config.json` 的 `auto_sync` 字段关闭。**不监听工作区文件变更** |
| 解析层 | Tree-sitter 引擎 | 解析变更文件，提取符号及调用关系 |
| 存储层 | SQLite（含 FTS5） | 存符号表、调用图、导入关系、全文索引。图谱放 `.codewiki/codewiki.db`（隐藏、gitignore） |
| 生成层 | Agent（LangGraph 编排） | 根据变更符号生成/更新 6 类 Wiki 文档到 `wiki/`（可见、gitignore、不提交），同时更新 `wiki/quickstart.md` 索引页 |
| 查询层 | CLI = MCP（统一工具面） | `codewiki init / sync / node / callers / callees / impact / search / explore`——同一套工具，终端和 Agent 都能调。Wiki 由 Agent 直接读文件（AGENTS.md → quickstart.md → 内链），图谱由 Agent 调 `codewiki_*` MCP 工具 |

### 5.2 构建流（冷启动，`codewiki init` 触发）
1. 锁定当前 checkout 分支名，记录于 `.codewiki/config.json`
2. Tree-sitter 全量扫描代码仓库，提取所有节点类型
3. 构建关系，批量写入 SQLite（AST 阶段只落 `contains` + 文件内 `references` + `unresolved_refs`；随后 ReferenceResolver 跨文件绑定成真边）
4. LLM 遍历核心符号，按模板生成 6 类文档，输出到 `wiki/`（同时注入代码锚点）→ 生成 `wiki/quickstart.md` 索引页（含项目概述 + 各文档链接列表）
5. 追加/更新目标仓库的 AGENTS.md / CLAUDE.md 引用段：「Wiki 从 `wiki/quickstart.md` 开始；代码事实查 `codewiki_*` 工具」
6. SQLite FTS5 索引文档内容，供符号搜索

### 5.3 更新流（增量，git 提交驱动）
> 与 codegraph 的 fs.watch 路线不同：CodeWiki 只响应**本地 git 提交**，不监听工作区文件改动。MCP Server 进程存活期间自动轮询（可在 `.codewiki/config.json` 设 `auto_sync: false` 关闭）。init 时锁定当前 checkout 分支，之后只看这个分支的提交。

1. **init 锁定分支**：首次建库时记录当前 checkout 的分支名（如 `feature/x`），后续固定轮询该分支引用；切到其他分支不会误触发。
2. **感知新提交**：MCP Server 进程存活期间自动轮询 `git rev-parse <branch>`，与 `last_indexed_commit` 比对，不一致即触发。进程生命周期 = 同步守护生命周期——客户端启动时 MCP 进程起来开始轮询，客户端退出则进程死、轮询停。
3. **取变更集**：`git diff --name-status C_old C_new` → 分类 A(新增)/M(修改)/D(删除)/R(重命名)。
4. **重索引变更文件**：M/A 重跑 Tree-sitter 提取 + `storeExtractionResult`（沿用 codegraph 跨文件边复活，见 4.3）；D 删节点 + 级联边；R 视作删旧 + 加新。
5. **定向重绑引用**：只对被改动符号相关的 `unresolved_refs` / 跨文件入边重跑 `ReferenceResolver`（不必全仓重解，省成本）。
6. **反向追溯受影响符号**：从变更符号沿 `CALLS`/`contains` 反向 2～3 层 → 受影响集合。
7. **定向重写 Wiki**：Agent 只重写受影响符号对应的文档段落（按锚点定位），删除符号的段落一并移除；涉及公开 API 签名改动时同步更新 `api/` 与 `modules/`。
8. **推进指针**：`last_indexed_commit = C_new`（幂等：HEAD 未动不触发；重复同步同 commit 则 diff 为空）。
9. **非祖先兜底**：若 `git merge-base --is-ancestor C_old C_new` 为 false（强推/reset/rebase 致 HEAD 跳变），整库全量重建，保证图谱与代码一致。

### 5.4 查询流（Wiki 优先，图谱兜底）
> 对标 openwiki 的 AGENTS.md → quickstart.md → 内链导航模式：Wiki 不经过 MCP、Agent 直接读文件。图谱走 MCP 工具（传递性聚合事实 grep 算不出），两套访问路径不冲突、不互绕。

**第一阶段：Agent 自动发现并阅读 Wiki**  
Agent 进项目时自动读 AGENTS.md（生态标准行为）→ 看到引用段「Wiki 从 `wiki/quickstart.md` 开始」→ 打开 `quickstart.md`，其中包含：
- 项目概述
- 文档地图（"Documentation map"——按 6 类的链接列表，openwiki 同款）
→ Agent 按需点击内链跳转相关 Wiki 页面。Wiki 内容完整则直接基于文档回答，并附锚点（file:line），流程结束。

**第二阶段：Wiki 不够 → 从锚点取符号 → 调图谱**  
Agent 判断 Wiki 过于笼统（缺少调用方、影响半径、精确类型层级等聚合事实），则：
1. 从 Wiki 段落中提取 `<!-- code_ref: file::symbol -->` 锚点
2. 调用图谱 MCP 工具：`codewiki_callers` / `callees` / `impact` / `node` / `search` / `explore`
3. 将图谱返回的精确代码事实融合进答案，标注 file:line

Agent 不会"跳过 Wiki 直接调图谱"——AGENTS.md 被自动读是生态标准行为，Wiki 入口在它面前；Agent 也不会"读完 Wiki 后 grep 源码绕过图谱"——调用链和影响半径 grep 本来就算不出来。

### 5.5 CLI = MCP（统一工具面）

CLI 和 MCP 是同一套工具，不存在"只有终端能用"或"只有 Agent 能调"的区别。codegraph 本身即此模型（`codegraph index` 既是 CLI 命令也是 MCP 工具）。

| 工具 | 作用 | 说明 |
| --- | --- | --- |
| `codewiki init` | 全量构建（见 5.2）：锁定分支 → 提取 → 图谱落库 → LLM 生成 Wiki + quickstart.md → 注 AGENTS.md | 用户和 Agent 都能调；新项目入口 |
| `codewiki sync` | 增量（见 5.3）：`git diff C_old C_new` → 重索引变更文件 → 定向重写受影响 Wiki 段落 | 用户和 Agent 都能调；MCP 进程默认自动轮询触发 |
| `codewiki node(symbol)` | 查符号详情 + 源码片段 | Agent 图谱查询 |
| `codewiki callers(symbol)` | 返回所有调用方列表 | Agent 图谱查询 |
| `codewiki callees(symbol)` | 返回所有被调用的下游 | Agent 图谱查询 |
| `codewiki impact(symbol)` | 影响半径（排除 contains 防爆炸） | Agent 图谱查询 |
| `codewiki search(query)` | FTS5 符号搜索 | Agent 图谱查询 |
| `codewiki explore(symbol)` | 图谱关系流（沿用 codegraph 预算算法，纯图谱内容，不掺 Wiki） | Agent 图谱查询 |

**自动同步机制**：
- MCP Server 进程启动时读 `.codewiki/config.json`，若 `auto_sync: true`（默认），则开始轮询分支引用
- 进程生命周期 = 同步守护生命周期：客户端启动 → MCP 进程起来 → 开始轮询；客户端退出 → 进程死 → 轮询停
- 关闭自动同步：`codewiki init --no-auto-sync`，或手动改 `.codewiki/config.json` 设 `auto_sync: false`
- 手动触发：随时调 `codewiki sync`（CLI 或 Agent 调均可）


## 六、技术选型

### 6.1 语言与运行时
| 组件 | 选型 | 说明 |
| --- | --- | --- |
| 主语言 | Python 3.10+ | 生态最完整；codegraph（TS）翻译到 Python 比 Java 更自然；官方 MCP SDK + 官方 tree-sitter SDK 双保险 |
| 包管理 | `uv` | Rust 实现，比 pip 快 10x，可靠锁文件 |
| 异步 | `asyncio` + `anyio` | FastMCP 底层，langgraph 兼容 |

### 6.2 图谱引擎（P1-P3）
| 组件 | 选型 | 说明 |
| --- | --- | --- |
| AST 解析 | `tree-sitter`（官方 `py-tree-sitter`，v0.26+，18M 周下载） | 预编译 wheel 全平台可用，官方维护（`tree-sitter` 同一组织） |
| 语法包 | `tree-sitter-java` 等独立 pip 包 | P1 先做 Java，后续按需加 Python/TS/Go/Rust/C/C++ |
| 图存储 + 全文索引 | `sqlite3`（标准库，零依赖） | FTS5 默认编译在 Python 3.10+ 全平台；WAL 模式支持并发读写 |
| Git 操作 | `GitPython` + `subprocess` 兜底 | `git diff --name-status` / `rev-parse` / `merge-base` |

### 6.3 MCP 服务 + CLI（贯穿全阶段）
| 组件 | 选型 | 说明 |
| --- | --- | --- |
| MCP Server | `mcp`（官方 `FastMCP`，23K star，v1.27.1，Anthropic 维护） | `@mcp.tool()` 装饰器 10 行起 stdio 服务；官方参考实现 |
| CLI | `typer` | 基于 click，类型注解自动生成帮助，子命令天然支持 |
| 配置 | `python-dotenv` + `.codewiki/config.json` | LLM API key 走 env；其余配置走 JSON |

### 6.4 Wiki 生成管线（P4）
| 组件 | 选型 | 说明 |
| --- | --- | --- |
| LLM 调用 | `openai` / `anthropic` 官方 SDK | 直接 SDK，不绕 langchain chat model 抽象 |
| 管线编排 | `langgraph` | StateGraph 多阶段流程（规划→组 prompt→并行生成→后处理）；`Send` API 并行 fan-out；`SqliteSaver` checkpoint/恢复；子图支持 subagent 并行研究（openwiki 模式） |
| 结构化输出 | `pydantic` | Wiki 段落 schema 校验（langgraph 和 FastMCP 也已依赖） |
| HTTP | `httpx` | FastMCP 自带 |
