## 深挖 OpenWiki agent 实现（修正此前误判）
- 此前我误称 OpenWiki "用 cli.tsx 定义 function-calling 工具"。实测代码：`createDeepAgent({ tools: [], backend: LocalShellBackend(...) })`，**tools 数组为空**。
- 真相：工具全部由 deepagents 的 LocalShellBackend 以"shell 后端"形式提供（ls/glob/grep/read_file/write_file/edit_file/execute），agent 靠跑 shell 命令探索仓库；不是自定义语义工具。
- langgraph 只用作 SQLite Checkpointer（跨 run 持久化），**不是手写的 StateGraph 节点机**。agent 循环（观察→思考→工具→观察）全在 deepagents 框架内部。
- 上下文管理：几乎无。单个连续 agent 会话跑到底，靠 system prompt 纪律("不要读每个文件"/"写完了就停")控制，无每模块重置、无硬 max-iter。
- 规划 = agent 自己写 `_plan.md` 文件（prompt 指令），非独立节点；允许 spawn 1-4 个**只读**研究子 agent（不准写文件），主 agent 唯一写者。
- Host 侧预扫描（Node 在调 LLM 前跑 git status/log/diff + 内容快照）产出稳定 gitSummary 喂给 prompt——这相当于我们的"项目地图"雏形，但 OpenWiki 不预生成目录树，agent 靠自己 `ls`/`rg --files` 发现结构。
- 对 P4 的启示：我们设计(每模块重置上下文 + planner/implement/finalize 节点 + explore() 语义工具)比 OpenWiki 更结构化，是为解决大库爆窗与探索低效；讨论时应对照这两套模型而非照搬。

## LangGraph 框架能力核实（BCD 讨论基础）
- 本地确认 LangGraph 1.2.9 已装，`create_react_agent` 可用（import 验证通过）。

## 差异A 讨论：plan 状态承载进度机制
- 用户要求：agent 知晓当前实现的 plan 分点；完成后把实现摘要回写 plan 对应节点；下一任务可见之前工作。
- 两种落地：方式一=plan 作为 StateGraph state(List[PlanItem]{id,type,target_path,depends_on,status,summary})，外层每轮取 pending 且依赖满足的项起 create_react_agent 会话、注入「当前项+plan全貌(含已完成summary)」，agent 完成回传 summary→外层写回 status=done（推荐：可控可审计，不依赖 agent 自觉写文件）；方式二=plan 落 `_plan.md` 文件，agent 自己 read_file+update_plan（贴近 OpenWiki，但依赖 agent 自觉易漏）。
- 关键设计点：①已完成项 summary 是给下一个 agent 看的轻量上下文(讲什么/核心符号/跨模块依赖)，非给人看的文档；②依赖顺序由外层代码保证(architecture 最后)，不交 LLM 判断；③显式告知 agent 当前实现第几项+给 plan 全貌。
- 待用户拍板：plan 载体(方式一 vs 二)、read_file 兜底范围(限定仓库根允许读任意源码 vs 严格封闭只给 .project_map.md+explore)、外层用 StateGraph vs 纯 Python 循环。

## 文件读写工具调研（避免重复造轮子）
- 事实：LangGraph 本身【不提供】文件读/写工具。已装 langgraph 1.2.9 / langgraph-prebuilt 1.1.0 只提供 ReAct 循环编排(create_react_agent)，文件 I/O 必须由我们自供工具；create_react_agent(tools=[...]) 接受任意 @tool，两种方案接入方式一致。
- 生态内现成轮子：langchain_community.tools.file_management 含 WriteFileTool/ReadFileTool/AppendFileTool/ListDirectoryTool/FileSearchTool 等 + FileManagementToolkit(root_dir+selected_tools 子集)。但【未安装】(本地只有 langchain-core/langgraph，无 langchain_community)，需 pip install langchain-community(较重依赖)。
- DeepAgents 的 FileSystemMiddleware + LocalShellBackend 暴露 ls/read_file/write_file/edit_file/glob/grep——这正是 OpenWiki 的 LocalShellBackend，我们刻意不抄这套 raw-shell 方案。
- 安全：LangChain 官方强调必须传 root_dir 防目录污染与 path-traversal 注入；toolkit 的 root_dir 即内置护栏。
- 设计要点：write_doc 必须限定 wiki/ 根(禁止写源码)；read_file 需同时覆盖 .project_map.md+任意源码(兜底)+已生成 wiki 文档，scope=仓库根只读。两 scope 不同→即便用 toolkit 也要实例化两个(root 不同)。
- 增量更新(差异B)：agent 读现有 doc→改→整篇写回(overwrite)即可，无需 edit/patch 工具；write_doc 默认 overwrite(重建=整篇重写，增量=agent 读全改全写回)。
- plan 载体(差异A)影响工具面：若 plan 存 StateGraph state(方式一)，agent 只需【返回】summary、由外层写回，无需 update_plan 工具；若用 _plan.md 文件(方式二)则需 edit_file/update_plan 工具→方式一工具面更干净。
- 待用户拍板：文件工具用 langchain-community 轮子(A) / 自写轻量 @tool 模块复用其 root_dir+护栏思路(B, 推荐, 依赖面最小) / 混合(C, wiki写用toolkit+源码读用@tool)。另:langchain_community 的 WriteFileTool 历史上有"追加而非覆盖"坑，需核实 overwrite 行为(选B则自写默认 overwrite 可控)。

## deepagents(Python) 调研：能否作为依赖 + 与 reactagent 区别 + 是否值得
- 关键澄清：OpenWiki 用的是 npm 版 deepagents(deepagentsjs v1.10.5, TS, repo=langchain-ai/deepagentsjs)；我们是 Python。
- 但【存在 Python 版 deepagents】(langchain-ai/deepagents, PyPI, `pip install deepagents`, 最新≈0.6.12, 2026 仍活跃更新)，本地当前未安装。它是 LangChain/LangGraph 官方出的 harness，`create_deep_agent()` 返回**编译好的 LangGraph 图**→与现有 langgraph 1.2.9 同生态，可接 streaming/checkpointer。
- 与 create_react_agent 的根本区别：react_agent=裸 ReAct 循环(think→act→observe)，只给 model+tools+prompt，规划/文件系统/子agent/上下文管理全自搭；deep_agent=在同样 ReAct 内核上**预置**：write_todos 规划工具 + 文件系统工具(ls/read_file/write_file/edit_file/glob/grep) + task 子agent 委派 + 长对话自动摘要(溢出对策) + 内置 system prompt 教模型用工具 + shell execute(可沙箱)。即"ReAct 引擎 + Claude Code 式脚手架"——正是我们前几轮讨论要自造的部分。
- 可定制：model / tools(追加到内置工具) / system_prompt(追加到默认) / middleware(加工具/钩子/改 prompt) / subagents(只读子 agent)。自定义工具用 tools=[...] 注入，与 create_react_agent 接入方式一致。
- 是否值得：分三选项——A(推荐试探)=外层 StateGraph 控序(architecture 最后)+plan承载进度(方式一)，内层 create_deep_agent 每模块一次(吃 explore 语义工具 + 按 scope 覆盖 fs 工具 + 关掉 execute shell)；拿到免费规划/fs/子agent/摘要，保住确定性排序+可控 scope+好调试。B=纯 create_react_agent 自实现(最轻最可控，但规划/fs/子agent/摘要全自己写)。C=整体 deepagents(最省事，但 architecture 最后确定性、scope 隔离、可调试性让渡给框架，风险最高)。
- 采用前必须验证的坑：①与 langgraph 1.2.9 版本兼容(装一次确认无冲突)；②能否**禁用内置 execute shell 工具**(我们安全模型刻意避免 raw shell，agent 只用 explore+scope 受限 read+write_doc)；③内置 fs 工具 scope 能否限制(write 限 wiki/、read 限仓库根只读)；④API 迭代快(半年 0.0.11→0.6.12)有漂移风险。
- 结论倾向 A：最贴合用户已定全部决策(单 Agent/顺序复用/每模块独立上下文/plan承载进度/探索自主/语义 explore 工具)。是否引入快速迭代稍黑盒的 harness 由用户拍板。
