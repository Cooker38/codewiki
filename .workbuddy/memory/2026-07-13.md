## codewiki 命令 PATH 排障（已解决）
- 症状：新开 cmd/ps 都识别不到 `codewiki`，用户误以为是"没刷新"或"没加系统变量"。
- 真根因：**用户 PATH 被畸形数据污染**——第 0 个条目混入 `:\Windows\System32\WindowsPowerShell\v1.0\powershell.EXE`（缺盘符 + 夹带 CR 回车符）。含控制字符/畸形条目会让 cmd 与 PowerShell 解析整条 PATH 失效，导致末尾的 CodeWiki 目录也不生效。与刷新无关。
- 修复：用一份干净的 17 条条目列表 `[Environment]::SetEnvironmentVariable("Path", ..., "User")` 重写用户 PATH。验证：长度 608 / 无 CR / 无畸形 powershell.EXE / 含 CodeWiki 目录。
- 验证 CLI 本体：`python -m codewiki.cli --help` 正常输出全部 8 命令（init/sync/node/callers/callees/impact/search/explore）。`codewiki.bat`/`codewiki.ps1` 均在目录内且内容正确。
- 结论：用户变量已足够（当前用户所有新窗口生效），无需写系统变量（且写系统变量需管理员权限）。用户开新窗口即可用。

## MCP Connection closed (-32000) 根因与修复
- 现象：WorkBuddy 信任 codewiki MCP server 后报 `MCP error -32000: Connection closed`。
- 真根因：**Windows 上 MCP `command` 不能是 `.bat`**。本机 `codewiki` 此前解析到 `codewiki.bat`，stdio 的 stdin/stdout 经 `cmd.exe` 包装层无法正确继承，客户端握手失败 → 连接关闭。serve 代码本身无误（FastMCP stdio + stdout 干净已确认；exe serve 在真实 stdin 下 ALIVE 无错）。
- 修复：
  - `pip install -e . --no-deps` 生成真正的 `codewiki.exe`（console_scripts 入口，绑定 managed python），不再依赖 bat。
  - 把 `codewiki.exe` 所在 Scripts 目录加到用户 PATH **最前**，确保 `codewiki` 优先解析到 exe。
  - 注册表 PATH 经 `reg query` 核实**本就干净**（18 条、无 CR、无畸形 powershell.EXE）。之前 PowerShell `[Environment]::GetEnvironmentVariable` 显示畸形是旧进程 PATH 快照的缓存误导，并非注册表真脏。
  - MCP 配置保持 `{ "command": "codewiki", "args": ["serve"] }`（现解析到 exe，stdio 稳）。
- 用户侧必要动作：**彻底重启 WorkBuddy** 继承新 PATH（其当前进程是旧的）。重启后 `codewiki` → exe → stdio 正常，不再 Connection closed。
